# GPUI performance baseline

This is a repeatable, macOS-first check for the event-driven GPUI window. It
uses the release binary, the app's opt-in counters, and Apple's process
samplers; it does not add a benchmark framework.

## Conditions and capture

Record the commit and runtime conditions with each result:

```sh
git rev-parse HEAD
rustc -Vv
sw_vers
cargo build --release -p rust-player
```

Use a fresh data directory for each run. Set `RUST_PLAYER_PERF=1`; the app
then writes one `[perf]` summary to `logs/player.log` when it quits cleanly:

```text
[perf] snapshots=… catalog_changes=… animation_frame_requests=… playback_renders=… render_avg_us=… render_max_us=… adapter_snapshot_translations=… adapter_library_translations=…
```

`snapshots` counts changed snapshots delivered to GPUI (identical publications
are already deduplicated by the runtime and the UI). `catalog_changes` counts
changes to search, detail, or library projections as observed by GPUI;
`adapter_snapshot_translations` and `adapter_library_translations` count the
actual source-adapter translation functions. The remaining four fields cover
animation-frame requests, active Playback Session renders, and their
total/max Rust render-construction cost. Catalog work therefore has separate
counters from animation work.

Capture process CPU and wakeups in a second terminal. Keep the sampler window
at 60 one-second samples (a 60-second observation window), and keep the PID
visible in the report:

```sh
PID=<rust-player-pid>
ps -p "$PID" -o pid,etime,%cpu,rss,command
sudo powermetrics --samplers tasks -i 1000 -n 60 > /tmp/rust-player-powermetrics.txt
ps -p "$PID" -o pid,etime,%cpu,rss,command
```

The `tasks` sampler contains the process wakeup rate and CPU sample. If the
machine requires a different privilege setup, run the same command through
the local approved `powermetrics` wrapper and keep its raw output.

## Paused-idle run (acceptance)

1. Start a fresh release process without `--fake`, sign in, start one Playable
   with Native Playback, then pause it. Keep the window open and idle; this
   exercises the real Playback Engine rather than a test double.

   ```sh
   DATA_ROOT="$(mktemp -d)"
   RUST_PLAYER_DATA_ROOT="$DATA_ROOT" RUST_PLAYER_PERF=1 \
     target/release/rust-player &
   PID=$!
   ```

2. Wait 10 seconds for startup and the initial library projection. Do not
   type, click, search, or play anything during the 60-s sampler window.
3. Run the `powermetrics` capture above, then quit with `⌘Q` so the summary is
   flushed. Save the raw sampler output and the final log line:

   ```sh
   tail -n 1 "$DATA_ROOT/logs/player.log"
   ```

The quiet-window expectation is zero changed snapshots after pause settles;
the startup/sign-in projection count is retained in the report and compared
across runs. A paused-idle pass fails if the process averages 1% CPU or more,
emits recurring snapshot publications, or exceeds 5 wakeups/second (p95)
without a platform event explaining them. For a credential-free GPUI smoke,
the same procedure may use `--fake`, but that result is not the acceptance
proof for Playback Engine idle behavior.

## Active Native Playback run

Run the same 60-second capture against a release process without `--fake`.
Complete sign-in, start one Playable with Native Playback, and let the track
run continuously. Perform one catalog search before starting the sampler, then
do not browse or search during the window. Quit with `⌘Q` after sampling and
save the `[perf]` line and raw `powermetrics` output.

An active pass should request animation frames at the display cadence (normally
about 60/s), with `playback_renders` tracking those requests. Report average
and maximum render-construction cost as a comparison trend; these counters
exclude GPUI layout/paint and are not a hard gate. Adapter translation counters
must not increase from animation frames. Catalog changes must stay flat during
the sampler window: catalog responses are event-driven and must not be
generated by animation frames. CPU and wakeups are reported as observations for
comparison, not mistaken for the paused-idle gate.

## Gate and report

| Scenario | Pass condition |
| --- | --- |
| Paused idle, 60 s | <1% mean process CPU; ≤5 wakeups/s p95; zero post-settle snapshot publications |
| Active Native Playback, 60 s | request rate within ±15% of display refresh; renders ≥95% of requests; render-construction timing is reported for comparison; adapter/catalog counters stay flat during the window |

Attach the commit, build/runtime conditions, sampler output, and the final
`[perf]` line to the result. Any unexplained threshold failure blocks a
performance-sensitive change until it is measured again.
